# Development

## Local database checks

Production is live, and preview and production share one Supabase database, so no rolled-back
check runs there (ADR 0085). Production gets read-only confirmation only. Every SQL assert in
`supabase/checks/` runs on a local Supabase stack instead.

Needs Docker Desktop running (`docker info` answers). The CLI runs through bunx, so nothing is
installed.

```bash
bun run supabase:start
```

The first run pulls the images and applies every file in `supabase/migrations/`, then
`supabase/seed.sql`. Later runs only start the containers.

```bash
bun run supabase:reset
```

Drops the local database and replays every migration plus the seed. Run it after adding a
migration.

```bash
bun run supabase:check supabase/checks/protection_assert.sql
```

`scripts/check-local.ts` wraps the file in `begin;` … `rollback;`, pipes it into `psql` inside the
`supabase_db_theatlas-queue` container, prints the file's last row (`… ok`), and exits non-zero on
the first error. It only reaches the local container. Files that open their own `begin;`
(`parity_assert.sql`) print two harmless warnings about the nested transaction.

Some checks' headers say to prepend their migration (`begin;` + `00NN_….sql` + the check). That
was for running on production before the migration was applied. Locally the migration is already
replayed, so pass the check file alone.

### When the stack hangs

Docker Desktop on Windows can wedge: it stays up and answers `docker ps`, but stops starting
containers. The symptoms:
- `supabase start` sits at "Starting database..." and `db reset` sits at "Recreating database...",
  with no error, for as long as you wait (15+ minutes on 2026-10-19);
- the db container shows `Created` in `docker ps -a`, never `Up`;
- realtime crash-loops with `Failed to detect IP version for DB_HOST: nxdomain`, a side effect of
  the db being down.

`supabase:start` and `supabase:reset` run `scripts/docker-preflight.ts` first. It does a bare
`docker run --rm alpine:3 true` (about 2 s when healthy) and fails after 60 s instead of hanging.
To recover:

```bash
docker desktop restart
```

Then kill any `supabase.exe` left waiting, run `bunx --bun supabase stop --no-backup`, and start
again. A fresh start replays every migration in under a minute.

### What the local stack differs in

- **`supabase/seed.sql` unschedules `queue-health`.** Migration `0013` schedules it to POST to
  the production `/api/cron/health` every 10 minutes. A local stack must never call production.
  `queue-retention` and `queue-settle` stay, as they only touch the local database.
- **`[analytics]` is off in `supabase/config.toml`.** It is only local logs, and on Windows it
  needs the Docker daemon exposed on TCP.
- The local Vault secret `queue_cron_secret` is generated by `0013` itself, so it never matches
  production's.

### Drift against production

Read-only, through the Supabase MCP `list_migrations`: the names must equal the files in
`supabase/migrations/`. Production versions are apply timestamps, not file numbers. Two known
quirks, both harmless: `0026` is recorded as `riot_switch_players`, and `0021` was applied after
`0022` and `0023` (it only schedules `queue-settle`, so the order does not change the result).
Checked through `0042` on 2026-10-18.
